# Datanotes: guide for Claude Code

Datanotes is the engine of a "second brain": Markdown notes run as typed, validated database
tables. A row is a note whose `table` property names a table; tables, views and bases are defined
in `datanotes/metastore.yaml`. Every write is validated, journaled and undoable. Programs use the
HTTP API (`datanotes serve`) or `datanotes/client`; agents use the MCP server `datanotes mcp`
(`src/mcp/`, its own process and a client of the HTTP API).
This file applies to every session, local (Windows) or in the cloud (claude.ai/code, Linux).

## Layout

- `src/core/` the engine (tables, validation, CHECKs, journal, queries, history). Reaches the vault
  only through `src/core/host.ts`; never imports `obsidian`.
- `src/node/` the headless host (a vault folder on disk) and the `datanotes` CLI (`cli.ts`, `service.ts`).
- `src/server/` the HTTP API: routes, OpenAPI, named tokens, webhooks, engine lock, change feed.
- `src/mcp/` the MCP server (`datanotes mcp`): stdio and Streamable HTTP, tools from `src/api/catalog.ts`.
  Imports only `src/api` and the MCP SDK (a devDependency, bundled into `dist/datanotes.cjs`); the
  engine never serves MCP itself.
- `src/api/` the published client. `src/api/catalog.ts` is the single source of the operations: names,
  tool descriptions, input schemas, OpenAPI. `src/api/` imports nothing else. It compiles with
  NodeNext (`tsconfig.api.json`): its relative imports end in `.js` (`./catalog.js`).
- `docs/` the Astro Starlight site (datanotes.dev), organized by area: Get started, Guides, Develop,
  Reference, Administration, Release notes. `docs/examples/` are runnable examples executed against a
  real engine (`run.ts`), shown on the guide pages of their area (`pages.ts`);
  `docs/examples/coverage.ts` checks every database option has one. A moved page gets a redirect in
  `docs/worker.js`.
  Pages generated by `scripts/gen-docs.mjs` are not committed: change the source, not the page.
  Every page also builds as `/<route>.md` (`docs/src/markdown-pages/`); the docs build fails if a
  page lacks a clean one. The build then copies those pages to `dist/docs/` (`scripts/copy-docs.mjs`):
  the npm package ships them, and `src/api/docs.ts` reads them for the MCP tools `list_docs`,
  `read_docs`, `search_docs` and for `GET /datanotes/manual/`.
- `tests/` vitest (`tests/README.md`, helpers in `tests/helpers/db-vault.ts`). `bench/` scale benchmark.
- `scripts/` layer check, docs generation, cloud setup, test vault tools.
- `deploy/docker/` the container image. `test-vault/` a small valid vault for development.

## Commands

```bash
npm ci                                  # dependencies (cloud sessions: done by the SessionStart hook)
npm run verify:fast                     # layers, types, tests related to uncommitted changes (seconds)
npm run verify                          # everything CI checks; must pass before a change is done
npm run verify:no-docs                  # the same without the docs build (no docs/node_modules)
npm run test:changed                    # only the tests related to uncommitted changes
npm test                                # all tests, in-memory vault (minutes: run in the background)
npm run test:node                       # same tests on the headless Node host
npx vitest run tests/<name>.test.ts     # one file: prefer this while iterating
node scripts/check-layers.mjs           # import boundaries between src/ layers
npx tsc -noEmit -skipLibCheck           # type check
npm run build:service                   # dist/datanotes.cjs (the CLI) + dist/api
npm run check:package                   # packed types: attw, publint, nodenext/node16/bundler consumer
cd docs && npm ci && npm run build      # docs site; runs every example (slow: background it)
npm run dev                             # engine on a temp COPY of test-vault/ (needs build:service)
npm run test-vault:check                # tests/test-vault.test.ts: the test vault is still valid
```

`npm run dev` prints the URL (a free port, or `-- --port N`), the vault copy, its store and the owner token
(also in `<store>/settings.json`). Call it with
`curl -X POST -H "Authorization: Bearer <token>" -H "Content-Type: application/json" -d '{}' <url>/datanotes/operations/list_tables/`;
`GET <url>/datanotes/docs` is the API reference. Run it in the background and stop it when done.

## The test vault

`test-vault/` (catalog `work.planning`: `person`, `project` tree with `ref_by` levels, `task` with
CHECKs, base `dated`, views `vw_open_tasks`, `vw_engineering`, `vw_project_tasks` with `{this.link}`,
plain notes in `Meetings/` and `Welcome.md`) is generated by the engine itself:
`npm run build:service && npm run test-vault:make`. Never edit it by hand; change
`scripts/make-test-vault.mjs` and regenerate. `tests/test-vault.test.ts` must keep passing: if an
engine change breaks it, fix the engine or, when the change is intended, regenerate the vault.

`tests/test-vault-ops/` runs every operation of `src/api/catalog.ts` on a fresh copy of the vault,
on the real service and in-process (helper `tests/helpers/test-vault.ts`, harness `harness.ts`).
`coverage.test.ts` fails naming any operation without a scenario: a new operation needs one. A
scenario marked `it.fails` with a `BUG:` title documents a known engine bug; when you fix the bug,
make it a plain `it` (`TEST_VAULT_BUGS=1` runs them as plain tests).

## Rules

- A change is done only when `npm run verify` passes: both test configs (in-memory and Node host),
  types, layers and the docs build. Iterate with `npm run verify:fast` or one test file.
- Work in batches, not in loops: run the full suite (or `npm run test:coverage`) once, collect every
  failure or uncovered branch, fix them all, then run once more to verify. While writing, run only
  the file you are changing, without coverage.
- A new or changed operation lives in `src/api/catalog.ts` (description, schema) and needs an example
  in `docs/examples/`; every option that defines the database needs one too (`coverage.ts`). Missing
  ones fail `tests/examples.test.ts` and the docs build.
- `metastore.yaml` changes only through operations (create_table, add_column, ...), never by hand,
  in tests, examples and the test vault alike.
- Keep the layers: `npm run check:layers` must pass.
- Every new error follows the standard (CONTRIBUTING.md, "Errors"; `src/core/hints.ts`): it says
  what is wrong, how to fix it (`hint`: the allowed values, the closest real name from the
  metastore, the right shape, the operation that looks it up) and where to look (`docs`: a
  `https://datanotes.dev/<route>.md#<anchor>` page). It gets a test of its hint and docs; a new docs
  topic must point to an existing heading (`tests/error-docs.test.ts`).
- Datanotes 3 stays 3 (CONTRIBUTING.md, "Compatibility" and "Names"): add, never take away a
  route, operation, argument, answer field, option or setting; a new meaning gets a new
  name. `tests/naming.test.ts` checks the naming guide;
  `tests/contract.test.ts` checks `contract/datanotes-3.txt` (`npm run contract:update` adds new
  lines). PATCH fixes, MINOR additions.
- Releases: set `version`, commit, publish a GitHub release `vX.Y.Z`; `.github/workflows/release.yml`
  publishes to npm (trusted publishing).
  Never run `npm publish` by hand.
- Never point tests or dev runs at a vault or engine you use for real data, and leave engines and
  services you did not start alone (the default port 27150 may be one). Use `npm run dev` (a temp
  copy of `test-vault/` on a free port) and temp folders; tests create their own.
- Pull requests from outside contributors are reviewed and run only in a cloud session, a VM or a
  devcontainer, never on a machine with real data: their tests, scripts and hooks run code.
- Do not commit or push unless asked. Never `git push --force`.
- On Windows, Node 24.0-24.15 aborts at random (exit 0xC0000409, vitest "Worker exited
  unexpectedly") on TCP connects to 127.0.0.1: a libuv bug fixed in Node 24.16.0. It is not a test
  or engine bug; use Node 24.16.0 or later (`npm run verify` warns).
- Line endings: Windows checkouts have CRLF through `core.autocrlf`; that is not a change. Do not
  mass-convert files. `*.sh` are LF (`.gitattributes`).
- English for code, comments, docs and commit messages.
- Docs prose follows the Vercel writing guidelines
  (https://raw.githubusercontent.com/vercel-labs/writing-guidelines/main/command.md; skill
  `writing-guidelines`), which win over the style of older pages: active voice, `you`, sentences
  under 20 words, no em dashes, acronyms spelled out, lists for three or more items, TypeScript
  examples, `<Steps>` for steps, code lines of 80 columns or less. Rewrite a page to them when you
  change it.

## Cloud sessions

`.claude/settings.json` runs `scripts/cloud-setup.sh` at startup/resume, only in the cloud: the
hook command itself checks `CLAUDE_CODE_REMOTE=true`. The script runs `npm ci` when needed and builds `dist/`; `DATANOTES_SETUP_DOCS=1`
also installs the docs dependencies. Its log is `$TMPDIR/datanotes-cloud-setup.log`. Bash timeouts are
raised (default 5 min, max 15 min); still run `npm test` and the docs build in the background or with
a long timeout. Background processes do not survive a paused VM: restart `npm run dev` after resume.
